# 用户模型限制与蒸馏行为风控实施说明

## 管理入口

- 用户模型限制：`/admin/model-bans`。也可在用户列表的更多菜单中打开当前用户的模型限制。
- 蒸馏行为风控：`/admin/distillation-risk`。与已有内容审核页面分开管理。
- 新增数据库迁移为 `246`–`260`，由已有迁移执行器应用；包含 Ent schema 和生成文件。

## 模型限制

策略按认证后的 `user_id` 生效，覆盖该用户所有分组和 API Key。规则引用供应商命名空间与确切模型身份，支持禁用模型、限制模型并发和限制模型 RPM，以及开始时间、到期时间、启停和原因。

模型身份目录登记标准模型及确切别名。别名可按传输平台、协议、primary/tool 角色和供应商上下文限定；不根据计费名称或字符串前缀猜测供应商。自定义模型需先登记。此实现不提供通配匹配或仅隐藏列表的独立规则。

写入通过版本 CAS 和管理员作用域的幂等键保护，保留不可变历史；人工修改不会删除行为风控拥有的规则。冲突保留前端草稿，可对比最新版本，确认放弃草稿后重新加载。

准入包含公开名称早期拒绝，以及路由、账号映射和工具模型确定后的最终判定。HTTP 转发、重试、WS 每轮最终帧、批图提交和 Live 创建均在上游发送边界检查。模型列表及模型广场按同一身份规则过滤。

**最终授权使用主库一致快照，读取同一 policy/catalog revision。** 这与旧设计稿中的缓存 fail-open 方案不同：明确禁用返回协议对应的 `403`，有活跃规则但身份无法唯一解析返回 `503`，策略存储故障返回 `503`；没有活跃规则时，未登记的新模型保持兼容。执行预算超限返回 `429`。分组白名单仍独立生效。

每次模型授权记录用户、请求/operation、policy/catalog revision、身份集合、结果、原因与延迟。审计写失败记录日志，不改变已得出的授权结果；不记录提示词正文或人工原因到客户端响应。

## 蒸馏风险

默认 `observe`，支持 `off / observe / enforce`。切换执行前要求七天观测；切回观测或关闭会解除自动限制，人工限制按自身生命周期处理。

每个 UTC 30 分钟窗口在结束后再等待 10 分钟封存。交互与异步批任务分别聚合，并分别维护连续高分、限制与恢复窗口；用户案件展示其中最严重的状态，不能跨请求类型拼接处分证据。七项信号为并发饱和、请求速率饱和、同 cohort/模型族 token p99、提示词精确重复率、模型/供应商广度、请求间隔规律性和输出/输入放大比。比例阈值可在页面修改，服务端严格校验并实际用于评分。

样本不足（200 个工作单元或 100,000 tokens 以下）不评分。缺失信号保留 unavailable，不重新放大其余信号权重；证据不完整不能推进自动限制或恢复连续窗口。连续两窗 ≥75 进入疑似，执行模式连续三窗 ≥85 可临时限速，连续四窗 <50 可恢复。自动限制默认两小时，连续最长六小时；到期后再次自动限制必须重新积累三个完整高风险窗口。人工限制必须填写原因与最多 24 小时的到期时间；豁免最多 30 天，不能绕过人工限制。页面提供审核、确认、驳回、限制、解除、豁免和证据事件。

提示词只提取相关 JSON 字段后生成按用户、按日派生的 HMAC，不保存正文。HMAC 七天清理；风险窗口/终态遥测 90 天，决策及风险事件 180 天，旧策略版本 365 天。当前策略、活跃任务和状态不明的任务不会被历史清理移除。

## 执行占用与恢复

执行操作先建立持久化 intent，Redis 原子预留与确认用户及模型预算，在发送前记录 attempt、payload hash、账号、供应商、版本、owner epoch 和已有资金 hold。退款继续由原有幂等计费流程处理。

恢复首次同步成功后才允许进入执行，之后每 20 秒后台运行。心跳失联或发送结果不明只转为 unknown，不按 TTL 释放，也不自动重提。普通槽位续期和启动清理不能给 unknown 占用重新设置 TTL；恢复会合并旧 attempt 的模型依赖并阻止原 owner 继续提交。正常 running 不重复恢复账号槽。批任务按声明 item 总数和已确认终态同步剩余数量，缺失 item 仍计入占用；只有 job 终态、item 数量完整且全部终态时回收各维度占用，回收成功写 `reclaimed_at`，可重试且不会重复释放。

非批任务的 unknown 不等于远端结束。Live 会话记录持久化 operation ID，跨实例或重启后仍可关联执行；仅远端明确返回会话不存在时才将对应用户的 running/unknown attempt 标为完成，再由后台回收。HTTP 创建成功、客户端断开、本地超时或租约过期均不能作为结束证据。无法确认的上游任务需要提供方确认或运维核对，不能直接清空 Redis 来解除限制。恢复对活跃 attempt 的查询尚未分页，大规模站点应结合活跃量观察恢复耗时。

## 验证与上线

验证包含后端单元测试、真实 PostgreSQL/Redis 集成、WS/Live 回归、前端类型检查与生产构建、中英文键完整性、管理模态框及风险页测试。前端全量 385 个测试文件、2,922 个测试通过，后端全量 unit、integration 及 go vet 通过。unit 复跑前曾有一条既有计费内存上限断言以 8,412,128 对 8,388,608 字节小幅超限；未调整断言，复跑通过。浏览器以 mock API 验证两个管理页在 375/768/1440 宽度和明暗主题下无页面横向溢出；这不替代真实上游端到端验收。

已按实际 CI 的 golangci-lint v2.14.0 检查本轮改动，新增问题为 0；同步修正开发指南中的旧版本说明。此结果不表示仓库既有 lint 问题已全部清理。

上线先应用迁移和部署前后端，在 observe 模式检查遥测完整性、目录解析及 worker 状态，再按观测结果启用执行。当前代码未自动部署或提交。
